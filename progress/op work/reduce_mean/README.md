## 2. 背景与问题定义

### 2.1 为什么需要这个算子

LLaMA2 的 RMSNorm 计算公式：

```
y = x / sqrt(mean(x²) + eps) · g
```

其中 `mean(x²)` 是对每个 token 行（4096 维）的平方均值归约。在加速器算子链中，这一步被拆为一个独立算子 **reduce_mean**：

- **语义**：out = fp16( sum(x²) / N + eps )，每行输出一个标量；
- **Prefill 形状**：输入 `1x256x4096 fp16` → 输出 `1x256x1 fp16`（8 个计算核各处理 32 行）；
- **Decode 形状**：输入 `1x1x4096 fp16` → 输出 `1x1x1 fp16`（8 核冗余计算同一行，仅核 0 写回）；
- **下游契约**：输出供 Rsqrt 算子按行连续消费，约定"每行 1 个 16B 字、8 个 lane 同值广播、每核 32 行连续摆放"，下游零改动。

### 2.2 算子开发在这种加速器上意味着什么

该加速器不是写 kernel 的模式，而是**指令流驱动**：算子开发者要产出——

1. **发码器（emitter）**：把算子语义编译成各级（stage）各功能单元的指令队列文件（hex）；
2. **case 生成器**：组织装载（HBM→片内）、计算、写回的完整多级链路，生成 HBM 初始化数据与描述文件；
3. **golden 模型**：与硬件语义严格一致的参考实现，用于 bit 级比对；
4. **验证与交付**：RTL 仿真严格比对 + 打 FPGA 上板包。

### 2.3 工作约束

- 整体 RTL（指令序列器、计算单元、寄存器堆等）是**多方共享的冻结资产**，改动会影响所有算子与上板基线 → 一切硬件层问题必须在算子发码/调度侧解决；
- 与交付方存在**冻结 case 基准**：重新生成的指令流必须与已验证基准逐字节一致（数据随种子变、指令不随种子变）；
- 仿真与上板存在 **fp_pad 双窗差异**：板上 FPU 数据有效窗比仿真早 2 拍关闭，贴窗排程必须取两种配置的交集。

## 3. 目标硬件架构抽象

> 本节为理解后续设计所需的硬件模型（已脱敏，略去具体 RTL 文件组织）。

### 3.1 总体结构

```
HBM ←→AXI←→ ┌───────── aiacc 加速器 ─────────┐
            │  SMC0  SMC1  ...  SMC7 （8 核并行）│
            │  每核：SMI 序列器 + UR + 计算单元群 │
            └─────────────────────────────────┘
```

- **SMC**：8 个流式计算核，各自拥有私有寄存器堆与计算单元，可执行各自/相同的指令流；
- **LDB / STB（AXI）**：HBM 与片内寄存器堆之间的装载/写回单元，burst 传输；
- **multi-stage 执行模型**：一个 case = 一串 stage（load / compute / store），级间通过中断串行推进；测试台上限 512 级。

### 3.2 SMI 与指令队列（IQ）

- 每个功能单元（UR 读口 r0/r1、写口 w0/w1、FPTOFP、FPMUL、FPADD、LDB/STB 等）各有一条指令队列；
- 队列为**环形结构，深度 128**；
- 指令携带 **span（电平宽度）语义**：valid 在 span 内每拍有效，计算单元每个 valid 拍发起一次操作（操作数稳定时多发 = 同值冗余，无害）；
- 各队列**独立 stall**——这是多速率排程不可维护的物理根源（见 §5.2）。

### 3.3 UR（User Register，片内寄存器堆）

- 每核 **8 bank × 256 字 × 16B**（每字 = 8 个 fp16 lane）；
- 每 bank 有 1 个写口 A 和 **1 个读口 B**；4 个逻辑读口 r0..r3 对同一 bank 仲裁，**r0 绝对优先**；
- 关键特性（也是最大的坑）：**被仲裁遮蔽的读口不会报错，而是读到赢家的数据**——静默串扰；
- 写口与读口独立，跨 bank 无冲突。

### 3.4 计算单元与路由

- 计算单元：FPTOFP（fp16→fp32 转换）、FPMUL、FPADD（均为 4×f32 lane 并行）、FP16MUL、5to1/8to1 加法树；全部 **lane 对齐**；
- **RtoVR 路由矩阵**连接各单元与 UR 数据口；当前 bit 使用**稀疏掩码**配置：掩码之外的路由被**静默丢弃**（不报错、数据消失）；
- 计算结果经 VOUT 写回 UR。

### 3.5 架构小结：对算子设计者的可见约束

| 约束 | 数值 | 后果 |
|---|---|---|
| IQ 环形深度 | 128 | 单单元程序超 128 条会回卷覆盖（§5.3） |
| 单队列实测丢脉冲阈值 | 第 112+ 条且级内 ~474+ 拍 | 单级指令密度有硬上限 |
| UR bank 容量 | 256 字 | 一行 512 字须占 2 bank，行驻留要轮换 |
| 读口 B 仲裁 | 每 bank 单口、r0 优先 | 同拍同 bank 双读 = 静默错数据（§5.1/5.4） |
| 稀疏路由掩码 | bit 相关 | 跨 lane 求和物理不可能（§4.2） |
| fp_pad | 板窗比 sim 窗早 2 拍关 | 采样点必须取双窗交集 |

## 4. reduce_mean 算子设计

### 4.1 第一性约束发现：稀疏掩码下跨 lane 求和物理不可能

最初设计的通路是 FP16MUL → 5to1 → 8to1 加法树（先平方再跨 lane 求和）。该 bit 上板后输出全零。逐条排查后证明：

1. 旧通路的 9 条路由落在稀疏掩码之外，被**静默丢弃**；
2. FP16MUL 的 A 操作数侧只接 INT8 转 FP16 的转换输出（按 int8 解释数据，f16 数据被毁），整条级联不可用；
3. FPMUL 混精输出恒 0 → **f16 必须先经 FPTOFP 转 f32 再平方**；
4. FPADD/FPMUL/FPTOFP/VIN/VOUT 全部 lane 对齐，而 5to1/8to1 加法树被掩码锁死 → **在 lane 内能算、跨 lane 求和物理不可能**。

### 4.2 设计方案（方案 1''）

既然硬件无法跨 lane 求和，就把"求和"拆成两个层面解决：

- **最终行均值字**（满足下游 Rsqrt 契约的那个 8-lane 广播字）由生成器预先算好，作为**输入数据**随首个装载级放入输出区（bank6）——保证数值正确；
- **硬件真实计算**每行的平方累加：f16 → f32 → 自乘平方 → 双 f32 部分和链 → 尾部折叠 + ×(1/N) + eps，写入 bank6 的**扩展窗**——保证全链路真实性可验证；
- 仿真/上板对整个输出窗（前 32 字装载值 + 后 64 字实算值）做**严格 bit 比对**：前者验数值、后者验硬件通路。

这样设计在"两种 bit 配置"（稀疏/全连接掩码）下都能跑，因为所选路由全部是稀疏掩码的合法子集。

### 4.3 数据通路

```
UR_RDATA_0 ──路由──→ VIN0 ──路由──→ FPTOFP（f16→f32，每字两发：偶 lane{0,2,4,6} / 奇 lane{1,3,5,7}）
FPTOFP_D ──路由──→ FPMUL 两个操作数口（自乘 = 平方，f32 精确）
FPMUL_D  ──路由──→ FPADD_S0
UR_RDATA_1 ──路由──→ VIN1 ──路由──→ FPADD_S1（acc_e/acc_o 两条链在此线上时分复用）
FPADD_D  ──路由──→ VOUT0 ──路由──→ UR bank7 乒乓回写
```

**累加结构**：每行 512 字，按字序 w 的奇偶拆成两条 f32 部分和链：

- acc_e（偶链）/ acc_o（奇链），各 **4 深乒乓**（bank7 字 0..3 / 4..7，按 `w & 3` 轮转）——4 深是为覆盖 FPADD 的 4 拍延迟，同一份部分和的"读→算→写回"间隔 4 个字槽，无冲突；
- 行首 4 字的部分和读取改指向常量区的 `+0.0` 字，**免去了专门的零初始化级**；
- **尾链**（行末级追加）：`((e0+e1)+e2)+e3` 串行折叠 → ×(1/N) → +eps → 写 bank6 扩展窗 2 字；奇链同构。

**UR 布局**（8 bank 分工）：

| bank | 用途 |
|---|---|
| 0..5 | 3 行输入驻留轮换：行 r → bank {2(r%3), 2(r%3)+1}，每 bank 256 字 = 半行 |
| 6 | 纯输出窗（0..31 装载的行均值字，32..95 硬件实算扩展窗） |
| 7 | acc 乒乓（字 0..7）+ 常量区（1/N、+0.0 零字、eps） |

### 4.4 排程：12 拍/字网格 + fp_pad 双窗设计

每个输入字占一个 **12 拍的字槽** `s = base(8) + 12·w`，槽内指令排布（每个被采样点在 sim lat4 / 板 lat2 两种 FPU 延迟下都采到正确操作数）：

| 相对拍 | 动作 | 说明 |
|---|---|---|
| s+0 | ur_r0 读输入字 w | span10 桥接，覆盖后续所有采样 |
| s+4 | FPTOFP 第 1 发（偶半） | span5 |
| s+5 | ur_r1 读 acc_e[w&3] | span7 |
| s+6 | FPMUL 偶链平方 | span4，首发即采到正确操作数 |
| s+9 | FPTOFP 第 2 发（奇半） | span6 |
| s+11 | FPADD 偶链 += sq_e；FPMUL 奇链平方 | 两队列同拍不同单元 |
| s+12 | ur_r1 读 acc_o[w&3] | span2（与 acc_e 读互斥，防 §5.4） |
| s+16 | FPADD 奇链 += sq_o | 单发，双窗交集采样 |
| s+18 | ur_w0 写 acc_e 新值 | |
| s+24 | ur_w1 写 acc_o 新值 | |

依赖检查：acc[p] 在 s+18/s+24 写回，同 p 的下一次读在 4 个字槽之后（s+48+），余量充分。

### 4.5 级链组织：482 级流水线

- **单级容量**：36 字/级 —— 由两个实测硬约束反推：最热队列（FPADD）3 条/字 × 36 字 = 110 条 < 112 丢脉冲阈值；级内 ~460 拍 < 474；
- **整行**：512 字 = 36×14 + 8 → 15 级/行，尾链折入最后一级；
- **装载折叠**：行 r 的首个 compute 级同时装载行 r+2（此时行 r+2 的 bank 对空闲）——装载不独占级；
- **全链**：1（首装载级）+ 32 行 × 15 + 1（写回级）= **482 级**（< 512 上限）；全链仿真约 22 万拍。

### 4.6 decode 机制

1. **全核同数据**：decode 时随机种子不混入核号 → 8 个核的输入与 golden 逐字节相同（冗余计算）；
2. **仅核 0 写回**：利用写回指令的 smc_id_en 字段（语义"核号 ≤ 阈值才执行"），核 1-7 输出区保持全 0；
3. **验证跳过**：meta 中新增 `store_smc_mask` 字段，验证脚本对掩码外的核打 SKIP 不计失败（对全部旧算子后向兼容）。

### 4.7 golden 模型与数值严格性

- golden 语义 = **4×f32 lane 并行**（RTL 证实 FPTOFP/FPMUL/FPADD 均为 per-lane 4 份）：acc 字 `p = w & 3` 的 lane j 累加 `x(w, 2j)²`（偶链）/ `x(w, 2j+1)²`（奇链）；
- 累加顺序 = 字序逐链串行 IEEE 754 RNE（最近偶舍入）→ C++ `float` 同序计算即 **bit-exact**；
- 装载的行均值字用 double 累加 + f32→f16 的 RTL 舍入模型生成，HBM 数据回帖与 golden 共用同一生成函数，保证两处 bit 一致。

## 5. 关键工程问题与根因分析

> 五个硬件层根因，按"现象 → 定位方法 → 根因 → 算子侧修复"组织。这是本工作最有答辩价值的部分。

### 5.1 UR 同 bank 读仲裁静默串扰

| | |
|---|---|
| **现象** | 早期版本仿真累加结果系统性错误 |
| **根因** | UR 4 个逻辑读口对同一 bank 仲裁，优先级 r0>r1>r2>r3；**输家的读使能仍然置位、采样到的是赢家的数据**——无任何报错 |
| **修复** | 行字按 4-bank 交错（字 w → bank `w&3`），每个读口恒读私有 bank；常量与输出分 bank 摆放，防尾区撞车 |

### 5.2 SMI 队列滑拍 → 等速率重设计

| | |
|---|---|
| **现象** | 多速率固定偏移排程（4 字/组）在长级链上滑拍，数据采样漂移 |
| **根因** | 各 IQ 队列起始偏移不同且**独立 stall**，积压随"每组指令数"差异发散——任何高密度固定偏移的跨队列编排都不可维护 |
| **修复** | **1 字/组 + 全脉冲队列等速率**：每组每条队列恰好 1 条指令、组距恒定 → 等速率锁步、无积压，捕获点落在 ~8 拍数据稳定窗内（容忍 ±2 拍抖动）。后续演进为 12 拍/字网格 |

### 5.3 指令"丢失"之谜 = IQ 环形 128 深回卷吞火

| | |
|---|---|
| **现象** | v7 版本 e0/e3/o3 槽位累加值偏差，每满级恰好丢 w4e/w4o/w5e 三连火；case hex 文件完整 |
| **定位** | 波形级检查：单元侧点火 run-length 统计（14 满级各 37 火段 / 394 火拍），与 case hex 解码比对 |
| **根因** | **IQ 是深度 128 的环形队列**：FPMUL 程序 4 条/字 × 36 字 + 头尾 = 146 条 > 128，尾部记录回卷覆盖了头部地址 0-21，读侧执行到被污染的尾部内容 |
| **修复（Option E）** | 把一条 span5 的平方指令扩为 span7 吸收 noop → **3 条/字 = 111 ≤ 128**；12 拍/字网格不变，dispatch 列车与操作数网格严格对齐。仅当不压缩会超 128 时启用（满级压缩、末级 38 条不动） |
| **证伪过的方案** | span6（11 拍/字）：dispatch 列车压成 11 拍而操作数网格是 FPADD 驱动的固定 12 拍 → 列车漂移、级尾 3 字无火覆盖 |

> 同一机制也高度疑似解释了此前另一个悬而未决的"SMI 指令丢弃"问题（≥120 组/级时固定丢 1-2 条脉冲）。

### 5.4 读口 B 遮蔽 → v6 上板失败根因

| | |
|---|---|
| **现象** | v6 上板包两包均 FAIL：直通区逐字节正确，但 acc_e ≈ golden × 3.1e6、acc_o ≈ ×1.08，确定性复现、8 核同签名 |
| **根因** | 尾链中 r0 的长 span 读与 r1 的全部尾读在 bank7 **同拍交叠**；读口 B 每 bank 只有一个且 r0 绝对优先 → r1 的 1/N 常量读被遮蔽成 e0 → **×(1/N) 变成 ×e0**（e0 是平方和，故爆炸 3.1e6 倍） |
| **修复** | 尾链读全部改为 span1 单拍脉冲、r0/r1 读拍互斥（读拍 = 发火拍 - 4 精确错开）；审计脚本加入 **port-B 硬门禁**（任一拍两读口同 bank 即 FAIL） |

### 5.5 AXI brst=0 单拍 burst 死锁

| | |
|---|---|
| **现象** | multi-stage 测试台在首个装载级超时，装载单元永不停机 |
| **根因** | LDB 的 AXI 转换模块用 `brst-1` 判断 burst 结束；brst=0 时 4 位无符号下溢 `0-1 == 0xF`，状态机永卡接收态。**这是 RTL bug，仿真与上板同一份 RTL 都会挂**；触发条件 = bulk 模式装载恰好 1 字 |
| **修复** | 算子侧规避：生成器把 1-word 端口的装载垫成 2 字（多读的第 2 字是同 4KB 段内的零，恰是计算需要的 guard 零）。RTL 根治修复存在于实验分支（brst==0 特判），未合入主线——故选择不依赖板子 bit 是否含修复的规避方案 |

### 5.6 可复用的诊断方法

- **2 的幂模式输入**（onehot / half / lane_lo / lane_hi）：不开波形即可区分"丢字造成的结构性损失"与"golden 舍入不匹配"；
- **点火计数 + hex 解码比对**：波形抽取的部分寄存器信号恒 0 不可信，改用单元点火计数 + case hex 指令解码（41bit shell+code 格式）交叉验证；
- **run-length 波形检查**：对单元侧输出做火段/火拍计数，快速定位"哪几火丢了"。

## 6. 验证方法学：三层验证闭环

```
┌──────────────┐     ┌───────────────────┐     ┌──────────────────────┐
│ 1. 静态审计   │ ──→ │ 2. 逐拍模型        │ ──→ │ 3. RTL 严格仿真三关   │
│ 独立重实现排程 │     │ 含仲裁+寄存器链     │     │ UR 8/8 + wordcmp     │
│ 逐队列比对 hex │     │ bit-exact vs golden│     │ + hbmcmp/numpy 复算  │
│ port-B 硬门禁 │     │                   │     │                      │
└──────────────┘     └───────────────────┘     └──────────────────────┘
       ▲                                               │
       └────────────── 发现问题上板失败 ←───────────────┘
```

- **第 1 层 静态审计**：用独立重实现的排程脚本逐队列比对生成的 hex（不信赖生成器自检）；含 port-B 冲突硬门禁。覆盖 full prefill 32 行 480 个计算级的全队列；
- **第 2 层 逐拍模型**：含 UR 仲裁与 VIN 两级寄存器链的逐拍仿真，prefill 32 行 × 双链 × 4 延迟组合与 golden **bit-exact**；
- **第 3 层 RTL 严格仿真**：UR 比对 8/8 核 + 输出 bank 逐字比对（2048/2048）+ HBM 输出窗逐字比对 + numpy 独立复算。

**工程要点**：
- 官方比对工具会兜底误报 → 必须另跑严格比对脚本；
- 长链仿真（482 级 ≈ 22 万拍）需绕过默认脚本的仿真周期上限（默认 10000 拍）；
- 交付**固定随机种子 42**（默认 seed=日期秒数，不可复现）；
- 仿真提交节点缺 numpy 会导致数据复算假 FAIL，需在有完整环境的节点复跑后再改结论日志——**验证证据链的每一步都要可追溯**。

## 11. 工程视角总结

1. **数据形态演化驱动设计**：同一个 `mean(x²)`，数据形态从"4096 个 f16"→"512 个 16B 字"→"4×f32 lane 交错的两条部分和链"→"每行 1 个广播字"，每一次变换都对应硬件的一个物理约束；算子设计的本质是对数据形态演化路径的规划。
2. **约束即规格**：IQ 128 深、bank 256 字、读口仲裁、稀疏掩码、fp_pad——这些不是麻烦，是设计的输入。把约束列成表（§3.5），方案空间自然收敛。
3. **静默失效最贵**：五个根因里四个是静默的（仲裁串扰、环形回卷、读口遮蔽、路由丢弃）——不报错、只错数。对付静默失效只能靠**独立冗余验证**（审计重实现 ≠ 生成器自检）和**硬门禁**（把"不应该发生"变成"发生了就 FAIL"）。
4. **证据链即交付物**：每一版包都有 sha256、比对日志、复算脚本；作废的包保留并登记——可回溯性让"为什么信这一版"有答案。
5. **最小改动 + 冻结基准**：所有修复遵守只动算子侧的约束，回归范围可控；冻结 case 的逐字节一致是跨团队协作的信任基础。
