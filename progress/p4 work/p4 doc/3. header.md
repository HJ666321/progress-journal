# iP4_t使用情况

---

### `ip4_t` 字段使用情况分析

| 字段名 | 位宽 | 是否在P4代码中被使用？ | 具体在哪里被使用 |
| :--- | :--- | :--- | :--- |
| `ver_ihl_dscp` | 16 | **否** | 在所有已分析的 `.p4` 文件中，没有找到对 `ip4.ver_ihl_dscp` 的任何读取或修改操作。 |
| `len` | 16 | **是** | 在 `p4/src/routing.p4` 的 `ac_swap_src_dst` 动作中被**修改**：`modify_field(ip4.len, 34);` |
| `iden` | 16 | **否** | 在所有已分析的 `.p4` 文件中，没有找到对 `ip4.iden` 的任何读取或修改操作。 |
| `frag` | 16 | **否** | 在所有已分析的 `.p4` 文件中，没有找到对 `ip4.frag` 的任何读取或修改操作。 |
| `ttl` | 8 | **否** | 在所有已分析的 `.p4` 文件中，没有找到对 `ip4.ttl` 的任何读取或修改操作。 |
| `proto` | 8 | **是** | 在 `p4/src/parser.p4` 的 `parse_ip4` 解析器中被**读取**，用于判断上层协议：`return select(latest.proto) { PROTO_MYH : parse_myh; ... }` |
| `csum` | 16 | **否** | 在所有已分析的 `.p4` 文件中，没有找到对 `ip4.csum` 的任何计算、验证或修改操作。 |

---

### 结论

在 `ip4_t` 这个头部定义的7个字段中，只有 **2个** 在P4程序的数据平面逻辑中被明确地使用了：

1.  **`ip4.proto`**: 在解析器（Parser）中被**读取**，用来判断数据包的下一个头部是否是自定义的 `myh_t` 协议头。这是实现自定义协议解析的关键一步。

2.  **`ip4.len`**: 在 `ac_swap_src_dst` 动作中被**修改**。这个动作是用来将一个请求包转换为响应包的（通过交换源目地址等）。修改 `ip4.len` 的值是为了确保响应包的IP头长度字段是正确的，因为 `remove_header(kv)` 动作会改变包的总长度。

**其他所有字段** (`ver_ihl_dscp`, `iden`, `frag`, `ttl`, `csum`) 尽管由解析器 `extract(ip4)` 提取了出来，但在后续的整个处理流程中**都没有被用到**。它们只是被动地“携带”过整个流水线，如果中间没有修改它们，它们会以原始值出现在最终的出站数据包中。
# 总长度

```p4
struct headers {
    eth_t eth;
    vlan_t vlan;
    ip4_t ip4;
    myh_t myh;
    kv_t  kv;
}
```

---

### 1. `eth_t` (以太网头)
- `dst`: 48位
- `src`: 48位
- `proto`: 16位
- **小计**: `48 + 48 + 16 = 112` 位

---

### 2. `vlan_t` (VLAN头)
- `vlan_id`: 16位
- `vlan_ethertype`: 16位
- **小计**: `16 + 16 = 32` 位

---

### 3. `ip4_t` (自定义IP头)
- `ver_ihl_dscp`: 16位
- `len`: 16位
- `iden`: 16位
- `frag`: 16位
- `ttl`: 16位
- `proto`: 16位
- `csum`: 16位
- **小计**: `7 * 16 = 112` 位

---

### 4. `myh_t` (自定义协议头)
- `sip`: 32位
- `dip`: 32位
- `fid`: 16位
- `ib`: 32位
- `seq`: 32位
- `ptype`: 16位
- `fill`: 16位
- **小计**: `32 + 32 + 16 + 32 + 32 + 16 + 16 = 176` 位

---

### 5. `kv_t` (键值对头)
- 包含 4 对 `key/value`，每部分都是 16 位。
- 总共有 `4 * 2 = 8` 个字段。
- **小计**: `8 * 16 = 128` 位

---

### 总计

现在我们将所有头部的小计加起来：

`112 (eth_t) + 32 (vlan_t) + 112 (ip4_t) + 176 (myh_t) + 128 (kv_t)`

`112 + 32 = 144`
`144 + 112 = 256`
`256 + 176 = 432`
`432 + 128 = 560`

所以，您定义的这一套完整的 P4 头部总共有 **560位**。

换算成字节就是： `560 / 8 = 70` 字节。

### 表格说明

*   **PHV容器类型**: 硬件内部有专门存放不同大小数据的“盒子”（容器）。这里 `01` 代表存放2字节数据的容器，`10` 代表存放4字节数据的容器。
*   **PHV容器索引**: 在同一类型的容器中，有很多个可以使用的“格子”，这个索引就是格子的编号。例如，`eth.proto` 被提取后，会存入“2字节容器”的**第0号格子**。

这样，后续的硬件模块（如密钥提取器 `KeyExtractConf`）就可以根据这个表格，通过指定“容器类型+容器索引”的方式，精确地拿到它想要的数据（例如，`KeyExtractConf` 可以配置说：“请把4字节容器的第2号格子里的数据（即`kv.kv_0`）拿来用”）。
