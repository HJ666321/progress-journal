### 核心目标：实现一个基于哈希的键值存储（Key-Value Store）

这段代码的核心功能是实现一个**哈希表**。它的目标是：对于数据包中携带的每一个键值对（如 `kv.k_00`, `kv.v_00`），能够在交换机的内存中高效地存储和更新它。

具体来说，它要解决一个核心问题：如何将一个可能无限大、类型任意的“键”（`key`），映射到交换机内部有限的、固定大小的内存（`register`）地址上。答案就是**哈希**。

### `tab_key_0` 的完整工作流程

我们将以 `key_0` 相关的所有组件为例，来逐步分解这个流程。

#### 1. `table tab_key_0` - 流程触发器

```p4
table tab_key_0 {
    actions {
        ac_key_0;
    }
    default_action : ac_key_0;
    size           : 1;
}
```
*   **做什么？** 这张表是整个流程的**起点/触发器**。
*   **怎么做？**
    *   它**没有 `reads` 块**，意味着它不匹配任何数据包字段。
    *   `default_action : ac_key_0;`：它的默认动作就是执行 `ac_key_0`。
    *   **结论**: 当 `p4/main.p4` 中 `apply(tab_key_0)` 被调用时，这张表会**无条件地、总是**触发 `ac_key_0` 这个动作。它的唯一作用就是启动key-0的处理流程。

#### 2. `action ac_key_0` - 指挥官

```p4
action ac_key_0() {
    bb_key_0.execute_stateful_alu_from_hash(cal_key_0);
}
```
*   **做什么？** 这个动作是**指挥官**，它不下场干活，而是命令一个黑盒去执行一个基于哈希的操作。
*   **怎么做？**
    *   它调用 `bb_key_0` 这个黑盒模块。
    *   `execute_stateful_alu_from_hash`: 这个方法指示黑盒，执行操作时所需的内存地址，不是直接给定的，而是需要从 `cal_key_0` 这个哈希计算单元获取。

#### 3. `field_list_calculation cal_key_0` - 地址计算器

```p4
field_list_calculation cal_key_0 {
    input {
        field_key_0;
    }
    algorithm    : crc16;
    output_width : REG_WIDTH_SHORT; // 值为 14
}
```
*   **做什么？** 这是一个**地址计算器**，负责将一个“键”转换为一个内存地址。
*   **怎么做？**
    *   `input { field_key_0; }`: 它的输入是 `field_key_0`。我们查看 `field_list field_key_0` 的定义：
      ```p4
      field_list field_key_0 {
          kv.k_00;
      }
      ```
      **事实证明**：哈希的输入**仅仅是**数据包中的 `kv.k_00` 字段，而不是我之前猜测的 `sip/dip` 等。
    *   `algorithm : crc16`: 它使用CRC16算法。
    *   `output_width : REG_WIDTH_SHORT`: 它输出一个14位宽的哈希值（因为文件开头定义了 `#define REG_WIDTH_SHORT 14`）。这个14位的哈希值将作为`register`的地址索引。

#### 4. `register reg_key_0` 和 `blackbox stateful_alu bb_key_0` - 存储与执行单元

这是整个系统的核心，也是最复杂的部分。

```p4
register reg_key_0 {
    width                 : 64;
    instance_count        : SIZE_ARRAY_SHORT; // 值为 16384
}

blackbox stateful_alu  bb_key_0 {
    reg                   : reg_key_0;
    condition_lo          : register_lo == 0;
    condition_hi          : register_lo == kv.k_00;
    update_lo_1_predicate : condition_lo;
    update_lo_1_value     : kv.k_00;
    update_hi_1_predicate : condition_hi;
    update_hi_1_value     : register_hi + kv.v_00;
    output_value          : predicate;
    output_dst            : meta.ib_0_predicate;
}
```
*   **做什么？** 它们共同构成了一个**带条件更新功能的键值存储单元**。
*   **怎么做？**
    *   `register reg_key_0`: 定义了一个名为 `reg_key_0` 的物理内存阵列。它有 `16384` 个槽位（`instance_count`），每个槽位宽64位（`width`）。`16384` 恰好是 `2^14`，与 `cal_key_0` 输出的14位地址完美对应。
    *   **`blackbox bb_key_0` 的内部逻辑**: 当 `ac_key_0` 触发它，并传入一个由 `cal_key_0` 计算出的14位地址（我们称之为`hash_addr`）后，硬件会执行以下原子的**读-改-写**操作：
        1.  **读 (Read)**: 从 `reg_key_0[hash_addr]` 读取出存放在那里的64位值。Tofino硬件会将这64位值拆成两部分：低32位（`register_lo`）和高32位（`register_hi`）。
        2.  **条件判断 (Condition)**:
            *   `condition_lo`: 检查 `register_lo`（即内存中存储的键）是否为0。如果为0，说明这个槽位是**空的**，`condition_lo` 为真。
            *   `condition_hi`: 检查 `register_lo` 是否等于当前数据包的 `kv.k_00`。如果相等，说明找到了**已存在的键**，`condition_hi` 为真。
        3.  **条件更新 (Update)**:
            *   `update_lo_1_predicate : condition_lo`: **如果** `condition_lo` 为真（槽位为空），则触发 `update_lo_1_value`。
            *   `update_lo_1_value : kv.k_00`: 将当前包的 `kv.k_00` 写入到 `register_lo`（低32位）中。**这相当于插入了一个新的键。**
            *   `update_hi_1_predicate : condition_hi`: **如果** `condition_hi` 为真（找到了匹配的键），则触发 `update_hi_1_value`。
            *   `update_hi_1_value : register_hi + kv.v_00`: 将`register_hi`（内存中存储的旧值）与当前包的 `kv.v_00` 相加，并将结果写回 `register_hi`。**这相当于对已存在的键进行了值的累加。**
        4.  **输出 (Output)**:
            *   `output_value : predicate`: 黑盒会根据 `condition_lo` 和 `condition_hi` 的真假情况，输出一个组合的状态码（`predicate`）。
            *   `output_dst : meta.ib_0_predicate`: 将这个状态码写入元数据 `meta.ib_0_predicate`，供后续模块使用。

### 结论与真实流程

**一句话总结：`tab_key_0` 及其相关组件实现了一个分布式的哈希表，用于对数据包中的第0个键值对（`k_00`/`v_00`）进行聚合。**

**真实流程:**

1.  `p4/main.p4` 调用 `apply(tab_key_0)`。
2.  `tab_key_0` 无条件触发 `ac_key_0`。
3.  `ac_key_0` 指挥 `bb_key_0` 去执行一个基于 `cal_key_0` 哈希结果的操作。
4.  `cal_key_0` 读取 `kv.k_00`，计算出一个14位的哈希地址 `hash_addr`。
5.  `bb_key_0` 使用 `hash_addr` 去 `reg_key_0` 内存中定位到一个64位的槽位。
6.  **情况A：新键**
    *   `bb_key_0` 发现槽位的前32位是0。
    *   它将 `kv.k_00` 存入前32位，并将 `kv.v_00` **直接存入**后32位（因为 `register_hi` 初始是0，`0 + kv.v_00 = kv.v_00`）。
7.  **情况B：键已存在**
    *   `bb_key_0` 发现槽位的前32位正好等于 `kv.k_00`。
    *   它读取槽位后32位的旧值，与 `kv.v_00` 相加，然后将新值写回后32位。
8.  最后，`bb_key_0` 将本次操作的结果（是插入还是更新）作为一个状态码，输出到 `meta.ib_0_predicate` 中。
