# parser-top

### 控制流说明

来自 `ctrl_s_axis` 接口的控制信号进入模块后，会首先通过 `mod_id` 和 `control_flag` 字段判断该控制包是否是发给当前解析器模块的。如果是，模块会从控制包中提取出目标地址 (`c_index`) 和要写入的数据 (`entry_reg`)，然后置高写使能信号 (`c_wr_en`)，将这些信息送给内部的 `parse_act_ram_ip` 实例，从而完成对解析器指令BRAM的写入操作。如果该控制包的目的地址不是当前模块，则会直接被透传到 `ctrl_m_axis` 接口，送往下一级。

### 控制信号表格

| 信号名称 (Signal Name)     | 来源 (Source)                                 | 方向 (Direction)     | 描述 (Description)                                     |
| :------------------------- | :-------------------------------------------- | :------------------- | :----------------------------------------------------- |
| `ctrl_s_axis_tdata`        | 上游模块 (Upstream Module)                    | 输入 (Input)         | 包含控制指令和数据的AXI-Stream总线。                   |
| `mod_id`                   | `ctrl_s_axis_tdata[368+:8]`                   | 内部信号 (Internal)  | 模块ID，用于识别目标模块是否是当前Parser。             |
| `control_flag`             | `ctrl_s_axis_tdata[335:320]`                  | 内部信号 (Internal)  | 控制标志位，用于识别是否为写BRAM的命令 (`16'hf2f1`)。 |
| `c_index`                  | `ctrl_s_axis_tdata[384+:8]`                   | 内部寄存器 (Internal)  | 要写入BRAM的目标地址。                                 |
| `entry_reg`                | `ctrl_s_axis_tdata_swapped[511 -: 160]`       | 内部寄存器 (Internal)  | 要写入BRAM的160位数据（解析指令）。                     |

## 为什么要这么取位数（结合数据进行分析）
### 简要说明

这套控制机制采用的是“带内管理”（In-band Management）的方式。简单来说，**控制指令被封装在一个标准的以太网UDP数据包的载荷（Payload）中**，通过网口发送给FPGA。FPGA的数据通路会捕获这个特殊的数据包，并将其路由到内部的控制路径（即 `ctrl_s_axis` 接口）。

这个512位（64字节）的 `ctrl_s_axis_tdata` 就代表了这个UDP载荷的第一个数据块。FPGA逻辑会从这个数据块的**固定偏移位置**解析出各个控制字段，就像解析一个自定义的应用层协议。

下面是各个字段位宽的合理解释：

*   **`entry_reg` (160位 / 20字节)**
    *   **原因**: 这是整个控制命令的“核心载荷”，即要写入BRAM的解析器指令本身。160位的宽度是由解析器指令的格式决定的，它定义了执行一个解析步骤所需的所有信息（例如，要匹配的头部字段、下一个状态、偏移量等）。这个宽度是流水线硬件设计时就已经确定的。

*   **`mod_id` (8位 / 1字节)**
    *   **原因**: 这相当于流水线中硬件模块的“地址”。在一个复杂的流水线中，可能有很多模块（多个Parser、多个Stage、Deparser等）都需要配置。8位地址空间允许系统对多达256个不同的模块进行寻址，这对于当前的设计来说绰绰有余。

*   **`c_index` (8位 / 1字节)**
    *   **原因**: 这可以看作是模块内的“寄存器或内存地址”。对于 `parser_top` 模块，它指定了要写入BRAM的256个条目中的哪一个。8位宽度正好对应了0-255的地址范围。

*   **`control_flag` (16位 / 2字节)**
    *   **原因**: 这是一个“魔术数字”或命令标识符，值为 `0xf2f1`。它的作用是验证这个数据包确实是一个合法的写指令，防止误操作。代码注释中也提到它可能是目的UDP端口号，因为UDP端口号就是16位的。CPU端的控制程序会向这个特定端口发送指令包，FPGA则检查这个值以确认命令的有效性。

### 可视化类比

您可以把整个64字节的UDP载荷想象成一张投递单：

| 字段 (Field)       | 位宽 (Bits) | 字节 (Bytes) | 投递单上的内容             | 解释                                     |
| :----------------- | :---------- | :----------- | :------------------------- | :--------------------------------------- |
| **`mod_id`**       | 8           | 1            | **收件部门** (例如, "解析部") | 确定FPGA中哪个大模块来处理这个指令。     |
| **`c_index`**      | 8           | 1            | **工位号** (例如, "0-255号")   | 确定写入该部门的哪个具体存储位置。       |
| **`control_flag`** | 16          | 2            | **快递单类型** (例如, "加急密件") | 确认这是一个合法的、需要立即处理的配置指令。 |
| **`entry_reg`**    | 160         | 20           | **文件内容**                 | 指令的核心，即要存入该工位抽屉里的文件。 |
| (其他/保留)        | 224         | 28           | (空白或其它信息)           | 64字节载荷中的剩余部分。                 |
| **总计**           | **512**     | **64**       | **整张投递单**               | 一个AXI-Stream数据包。                   |
# stage

与 `parser_top` 类似，`stage` 模块也通过 `c_s_axis` 接口接收控制指令，但其内部处理更为精细，因为它需要将指令分发给不同的子组件，例如 `key_extract`、`lookup_engine` 和 `action_engine`。这里的核心控制逻辑位于 `lookup_engine` 内部的 `lke_cam_part.v` 模块中，它负责更新TCAM条目。

### 控制流说明

来自上游的控制包（封装在UDP载荷中）进入 `stage` 模块。`stage` 模块像一个路由器，会将控制包逐级传递给内部的 `key_extract`、`lookup_engine` 等子模块。当控制包到达 `lookup_engine` 时，其内部的CAM控制器会进行多级地址匹配：首先，它会检查 `mod_id` 的高5位是否与当前 `stage` 的ID（`STAGE_ID`）匹配；如果匹配，则继续检查 `mod_id` 的低3位是否与 `lookup_engine` 的ID（`LOOKUP_ID`）匹配。同时，它也会验证 `control_flag` (`0xf2f1`) 和用于区分资源的 `resv` 字段（`4'b0` 表示写TCAM）。只有当所有这些条件都满足时，它才会从控制包中提取TCAM的地址（`c_index_cam`）和数据（`cam_entry_reg`），并执行写操作。如果任何一级地址不匹配，控制包就会被原封不动地传递到下一个模块。

### 控制信号表格

| 信号名称 (Signal Name)   | 来源 (Source)                                  | 方向 (Direction)    | 描述 (Description)                                                        |
| :----------------------- | :--------------------------------------------- | :------------------ | :------------------------------------------------------------------------ |
| `c_s_axis_tdata`         | 上游模块 (Upstream Module)                     | 输入 (Input)        | 包含控制指令和数据的AXI-Stream总线 (512-bit)。                               |
| `mod_id`                 | `c_s_axis_tdata[368+:8]`                       | 内部信号 (Internal) | 模块ID。高5位(`[7:3]`)匹配`STAGE_ID`，低3位(`[2:0]`)匹配`LOOKUP_ID`。 |
| `control_flag`           | `c_s_axis_tdata[335:320]`                      | 内部信号 (Internal) | 控制标志位，值为`16'hf2f1`时表示合法指令。                               |
| `resv`                   | `c_s_axis_tdata[376+:4]`                       | 内部信号 (Internal) | 资源选择位。`4'b0`表示目标为TCAM。                                        |
| `c_index_cam`            | `c_s_axis_tdata[384+:8]`                       | 内部寄存器 (Internal) | 要写入TCAM的目标地址 (0-255)。                                           |
| `cam_entry_reg`          | `c_s_axis_tdata_swapped[511 -: 205]`           | 内部寄存器 (Internal) | 要写入TCAM的205位数据，包含key和可能的掩码。                                      |
| `c_wr_en_cam`            | 内部控制状态机 (Internal FSM)                    | 内部寄存器 (Internal) | TCAM的写使能信号。                                                        |
| `c_m_axis_tdata`         | `c_s_axis_tdata` (当非目标模块时)               | 输出 (Output)       | 将非本模块的控制信号透传到下游。                                          |
