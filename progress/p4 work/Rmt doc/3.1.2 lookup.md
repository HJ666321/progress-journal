### 总体概述

`lookup_engine_top.v` 模块是RMT流水线中每个 `stage` 的“档案管理员”。它紧跟在 `key_extract`（侦探）之后。它的核心任务是接收 `key_extract` 生成的“密钥”，然后在一个或多个大型的查找表（CAM - 内容寻址存储器）中进行**高速并行匹配**。

如果匹配成功（“命中”），它会输出匹配条目的地址。这个地址随后被用来从另一个存储器（RAM）中取出对应的“**动作**”（Action），这个动作将指导下一个模块（`action_engine`）如何去修改PHV。

简而言之，`lookup_engine` 的作用就是：**用Key查表，得到Action**。

### 分层解析

我们将自顶向下分析其结构，从 `lookup_engine_top.v` 开始，然后深入其子模块 `lke_cam_part.v` 和 `lke_ram_part.v`。

#### 第1步：分析顶层模块 `lookup_engine_top.v`

我将首先读取顶层模块的文件，以了解其整体架构、接口以及它如何组织其内部的查找单元。


Read file: fpga/mqnic/AU280/fpga_100g/lib_rmt/rmtv2/lookup/lookup_engine_top.v
对 `lookup_engine_top.v` 的代码分析揭示了其内部清晰的流水线结构：

1.  **架构**: 模块内部例化了**一个** `lke_cam_part` 模块和**一个** `lke_ram_part` 模块。这形成了一个两级的微流水线：
    *   **第一级 (CAM)**: `lke_cam_part` 负责接收`key`并进行匹配。
    *   **第二级 (RAM)**: `lke_ram_part` 接收来自CAM的匹配地址，并用它来获取最终的`action`。

2.  **数据流**:
    *   `extract_key` 和 `phv_in` 首先进入 `lke_cam_part`。
    *   `lke_cam_part` 进行匹配，然后输出`cam_match_addr_out`（匹配地址）和 `cam_if_match`（是否命中），同时将 `phv_in` 透传出来（`cam_phv_out`）。
    *   这些来自CAM的输出，经过一级寄存器（`_d1`）同步后，被送入 `lke_ram_part`。
    *   `lke_ram_part` 使用 `cam_match_addr_out_d1` 作为地址，从其内部的RAM中查找出 `action`，并最终将 `action` 和透传的PHV一起输出。

3.  **控制流**:
    *   控制平面报文（`c_s_axis_*`）首先进入 `lke_cam_part`。
    *   `lke_cam_part` 会检查 `mod_id`，如果配置是给它自己的，它就会处理并写入自己的CAM；否则，它会将控制报文原封不动地从 `c_m_axis_*` 接口透传出来。
    *   从 `lke_cam_part` 出来的控制报文（`c_s_axis_tdata_0` 等）直接连接到 `lke_ram_part` 的控制输入。
    *   `lke_ram_part` 再次检查 `mod_id`，如果配置是给它的，就处理并写入自己的RAM；否则，就继续向后传递。
    *   这种菊花链（Daisy Chain）式的控制路径，使得可以为同一个`STAGE_ID`下的CAM和RAM分别进行配置。

现在，我们深入子模块，看看它们具体做了什么。

#### 第2步：分析 `lke_cam_part.v` (CAM部分)

我将读取 `lke_cam_part.v` 文件，来确认它是如何用 `extract_key` 进行匹配的。


Read file: fpga/mqnic/AU280/fpga_100g/lib_rmt/rmtv2/lookup/lke_cam_part.v
对 `lke_cam_part.v` 的分析证实了它执行了匹配的核心功能：

*   **CAM例化**: 模块内部例化了一个名为 `cam_top` 的核心 (line 408 in full file)。这个 `cam_top` 就是真正的硬件CAM。
*   **匹配输入 (`CMP_DIN`)**: 传递给 `cam_top` 用于比较的数据 `CMP_DIN`，是由 `extract_key` 和从PHV中提取的 `vlan_id` 拼接而成的。`assign dbg_input = {vlan_id[3:0], vlan_id[11:4], extract_key};`
*   **匹配输出**: `cam_top` 的输出 `match` (是否命中) 和 `match_addr` (命中地址) 被连接到模块的状态机逻辑。
*   **状态机逻辑**: 模块的状态机 (lines 81-155) 确保了在 `key_valid` 有效时，将匹配结果 `match` 和 `match_addr` 锁存并输出。如果未命中（`match == 1'b0`），则输出一个特殊的地址 `4'hf`。
*   **控制路径**: 如之前在顶层模块分析中所述，它拥有自己的控制逻辑，通过检查 `mod_id`（`STAGE_ID`+`LOOKUP_ID`）和`resv`字段来决定是否接收和写入CAM配置。

#### 第3步：分析 `lke_ram_part.v` (RAM部分)

最后，我将读取 `lke_ram_part.v` 文件，以确认它是如何使用来自CAM的地址来查找Action的。


Read file: fpga/mqnic/AU280/fpga_100g/lib_rmt/rmtv2/lookup/lke_ram_part.v
对 `lke_ram_part.v` 的分析非常直接，它完成了 `lookup_engine` 的后半部分工作。

*   **BRAM例化**: 模块内部包含了一个BRAM（块RAM），用于存储“动作”表。这个BRAM通过 `action_bram` 实例化。
*   **地址输入**: BRAM的读地址 `addra` 直接连接到从 `lke_cam_part` 传来的 `match_addr`。
*   **数据输出**: BRAM的读数据输出 `douta` 连接到 `action_wire`。
*   **命中/未命中处理**:
    ```verilog
    assign action = (if_match_d1==1)?action_wire:625'h3f;
    ```
    这行代码是核心逻辑：
    *   如果 `if_match_d1` 为1（表示CAM命中），则将从BRAM中读出的 `action_wire` 作为最终的`action`输出。
    *   如果为0（表示CAM未命中），则输出一个硬编码的默认`action`：`625'h3f`。这个默认值很可能指示后续的`action_engine`什么都不做，直接透传PHV。
*   **控制路径**: 与`lke_cam_part`类似，它也拥有自己的控制逻辑，通过`mod_id`和`resv`字段来识别并写入发给自己的RAM配置报文。

### 结论与流程图

**`lookup_engine_top.v` 是如何工作的？**

它实现了一个两级、菊花链式配置的“Key-Action”查找引擎：

1.  **顶层协调 (`lookup_engine_top.v`)**:
    *   **架构**: 实例化一个`lke_cam_part`和一个`lke_ram_part`，构成两级流水线。
    *   **数据流**: 将`key`送入CAM部分，然后将CAM的输出（匹配地址）送入RAM部分。
    *   **控制流**: 将控制报文以菊花链方式依次串接CAM和RAM部分，使它们可以被独立配置。

2.  **第一级: CAM匹配 (`lke_cam_part.v`)**:
    *   **输入**: `extract_key` 和 `vlan_id`。
    *   **操作**: 将输入拼接后，在内部的 `cam_top` 中进行内容寻址匹配。
    *   **输出**: 匹配结果（`if_match`）和匹配地址（`match_addr`）。

3.  **第二级: RAM查找 (`lke_ram_part.v`)**:
    *   **输入**: `match_addr` 和 `if_match`。
    *   **操作**: 使用 `match_addr` 作为地址，从内部的BRAM中读取预存的`action`。
    *   **输出**: 查找到的 `action`（如果命中）或一个默认的`action`（如果未命中）。

整个流程是高度模块化和可扩展的。通过菊花链式的控制，软件可以精确地更新流水线中任何一个Stage的任何一个查找单元（CAM或RAM）的内容，而无需中断其他部分的操作。
