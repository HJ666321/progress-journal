```cpp
bool FPGATable::emitConf(struct StageConf *stg_conf, int &st_stg, int &nxt_st_stg) {
	int start_stage = st_stg;
	bool placed = false;
	// 1. place key conf
	for (auto i=start_stage; i<5; i++) {
		if (stg_conf[i].occupied) continue;

		if (key_res_ok(stg_conf[i])) {
			emitKeyConf(stg_conf[i]);
			st_stg = i+1;
			placed = true;
			break;
		}
	}
	if (!placed) { return false; }

	// 2. place action conf
	// a. find a free stage for ram configuration
	placed = false;
	for (auto i=st_stg; i<5; i++) {
		if (stg_conf[i].occupied) continue;

		// find a place
		st_stg = i;
		placed = true;
		break;
	}
	if (!placed) { return false; }
	// b. do the real job
	nxt_st_stg = emitRAMConf(default_act_path, stg_conf, st_stg);

	return true;
}
```

这段真实的代码揭示了分配的核心逻辑，它远比之前想象的复杂。一张 P4 表的**匹配部分 (Key)** 和**动作部分 (Action)** 是**分开独立进行分配**的。

**分配流程详解：**

1.  **`emitConf` 函数接收起始阶段 `st_stg`**: `FPGAControl` 告诉这张表：“你最早可以从第 `st_stg` 级开始放”。

2.  **第一步：为“匹配键 (Key)”分配阶段**
    *   `for (auto i=start_stage; i<5; i++)`: 代码从被允许的起始阶段 `start_stage` 开始遍历。
    *   `if (stg_conf[i].occupied) continue;`: 跳过已经被占用的阶段。
    *   `if (key_res_ok(stg_conf[i]))`: 调用 `key_res_ok()` 检查当前阶段 `i` 的硬件资源是否足以容纳这张表的“匹配键”。
    *   `emitKeyConf(stg_conf[i]);`: 如果资源足够，就调用 `emitKeyConf()` 将“匹配键”的具体配置写入到 `stg_conf[i]` 中。
    *   `st_stg = i+1;`: **关键步骤**。更新 `st_stg` 为当前阶段的下一个阶段 `i+1`。这意味着接下来的“动作”部分，必须在“匹配键”之后开始寻找位置。
    *   `break;`: 找到位置后立刻跳出循环。

3.  **第二步：为“动作 (Action/RAM)”分配阶段**
    *   `for (auto i=st_stg; i<5; i++)`: 代码从**刚刚更新过的 `st_stg`**（即匹配键阶段的下一级）开始，为“动作”部分寻找一个空闲的起始位置。
    *   `st_stg = i; break;`: 找到第一个空闲阶段后，将其记录在 `st_stg` 中并跳出循环。
    *   `nxt_st_stg = emitRAMConf(default_act_path, stg_conf, st_stg);`:
        *   **最终的分配决策者是 `emitRAMConf`**。它负责将这张表的所有“动作”配置写入流水线。
        *   它从 `st_stg` 开始，可能会占用**一个或多个**连续的硬件阶段来存放所有的动作逻辑。
        *   执行完毕后，它会返回**它所占用的最后一个阶段之后，第一个可用的阶段编号**，并存入 `nxt_st_stg`。

4.  **返回到 `FPGAControl`**: `emitConf` 执行完毕后，`FPGAControl` 会读取 `nxt_st_stg` 的值，并将其作为下一张 P4 表的 `st_stg` (起始阶段) 传入，从而形成一个级联式的分配链。

### 最终的、确切的分配策略

P4 表到硬件流水线阶段的分配是一个**串行的、分两步走**的过程：

1.  **为“匹配键”分配一个阶段**：从允许的起始位置开始，找到第一个资源足够且空闲的阶段。
2.  **为“动作”分配一个或多个阶段**：从“匹配键”阶段之后开始，找到一片连续的、空闲的阶段来存放所有的动作逻辑。

这个过程确保了同一张表的“动作”总是在其“匹配键”之后执行，并且不同的 P4 表按照在 `applied_tables` 列表中的顺序，依次被放置到流水线的可用空闲位置上。

### 1. `KeyExtractConf` 和 `CAMMaskConf` - (匹配键配置)

这两个配置项由 `printExtractorConf` 函数 (`emit-pkt.cpp:81`) 生成，用于配置流水线阶段的**键提取逻辑**。

*   **调用者**: `FPGATable::emitKeyConf` (`fpga-table.cpp`)

*   **示例格式**:
    ```
    KeyExtractConf 001010000000000000000000 011010001001...
    CAMMaskConf    001010000000000000000001 111111110000...
    ```

*   **代码解析**:
    *   **标签**: `os << "KeyExtractConf ";` 和 `os << "CAMMaskConf ";` 直接写入这两个标签。
    *   **二进制串第一部分 (地址)**: 它们都调用 `printStageInd(...)` (`emit-pkt.cpp:40`) 生成前 24 个比特。
        *   `printStageInd` 接收 `module`, `stg_num`, `entry_ind` 等参数。它将这些参数打包成 3 个字节（24位），作为这个配置项在 FPGA 内部的地址。
        *   **`0-7` 位**: 模块ID (e.g., `MODULE_EXTRACTOR` = 1)
        *   **`8-15` 位**: 模式/保留位
        *   **`16-23` 位**: 阶段号 (0-4)
    *   **二进制串第二部分 (数据)**:
        *   `KeyExtractConf`: 这一部分由 `key_conf` 结构体中的 `op_6B_1`, `op_4B_1` 等成员决定。这些 `op` 定义了如何从输入的报文头向量 (PHV) 中抓取不同长度（6字节、4字节、2字节）的字段，以拼接成 P4 表的匹配键。
        *   `CAMMaskConf`: 这一长串的 `1` 和 `0` 由 `key_conf.validity_flag` 决定。它生成一个掩码 (mask)，用于支持三态匹配 (Ternary Match)。`1` 代表“关心 (don't care)”，`0` 代表“不关心 (care)”。

### 总结

生成的 `.txt` 配置文件是一个高度结构化的、给 FPGA 加载程序看的“指令脚本”。

| 标签 | 生成函数 (emit-pkt.cpp) | 含义 |
| :--- | :--- | :--- |
| **`KeyExtractConf`** | `printExtractorConf` | **定义如何拼接匹配键**：指定从报文的哪些位置抓取数据来形成 P4 表的 Key。 |
| **`CAMMaskConf`** | `printExtractorConf` | **定义匹配掩码**：为 `KeyExtractConf` 生成的键提供一个 Ternary 掩码。 |
| **`CAMConf`** | `printCAMConf` | **定义流表匹配规则**：向 TCAM 中写入具体的流表条目，比如“当源 IP 是 X 时匹配”。 |
| **`RAMConf`** | `printRAMConf` | **定义流表动作参数**：配置与 `CAMConf` 中规则相对应的动作，比如“修改目标 MAC 地址为 Y”。 |

每一行配置都通过 `printStageInd` 生成的地址头来精确定位到要配置的硬件模块（哪个阶段、哪个子模块、哪个条目），后续的二进制数据则是对该模块寄存器的具体赋值。
